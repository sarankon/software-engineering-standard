# Core

- Project: `software-engineering-standard`.
- Purpose: develop a versioned Software Engineering Standard (SES) for consistent software development across projects, including AI-assisted development.
- Repository branch: `main`.
- Global SES is the reusable source of truth; each consuming project owns its `project_context/` and must not be overwritten wholesale during upgrades.
- Major SES areas: `standards/`, `ai_development/`, `blueprints/`, `migrations/`.
- Standard taxonomy selected: `principles/`, `foundation/`, `architecture/`, `development/`, `presentation/`, `data/`, `integration/`, `security/`, `quality/`, `operations/`, `maintenance/`.
- Rule design: stable Rule IDs (`SES-{CATEGORY}-{NUMBER}`), lifecycle (`draft`, `proposed`, `active`, `deprecated`, `removed`), levels (`MUST`, `MUST NOT`, `SHOULD`, `SHOULD NOT`, `MAY`), applicability, and sections for Requirement, Rationale, Examples, Verification, Exceptions, and Migration.
- `standards/SPECIFICATION.md` defines the canonical Rule format; `standards/rule-template.md` is the authoring template.
- AI development model: `AGENTS.md` is the project AI entry point; AI should load project context, identify applicable standards, plan, implement, verify, update context, and complete.
- Project Context Blueprint: `project_context/` contains `development_standard/`, `ai_development/`, `knowledge_base/`, `decisions/`, and `state/`; Blueprint is independently versioned and upgrades require migration guidance.
- Foundation files complete as substantive Drafts: `project-structure.md`, `repository.md`, `configuration.md`, `environment.md`, `dependencies.md`, `documentation.md`, `ai-entry-point.md`.
- Foundation principle: SES defines structural responsibilities and boundaries, not a universal physical directory layout. Projects may adapt physical structure to technology and architecture.
- `project-structure.md`: technology independence, separation of concerns, discoverability, consistency, project-context isolation, no unnecessary structure, required responsibilities, AI discoverability, exceptions, verification, migration.
- `repository.md`: source control, default branch, branching, commits, collaboration/review, repository hygiene, secret exposure remediation, release traceability, repository configuration, exceptions, verification, migration. No mandated Git Flow, trunk-based development, PR/MR, or universal workflow.
- `configuration.md`: configuration classification, ownership, externalization, safe defaults, environment-specific configuration, secret handling, naming/structure, validation, security, exceptions, verification, migration. No mandated configuration format/platform.
- `environment.md`: environment definition/purpose, lifecycle, isolation, reproducibility, environment-specific differences, data handling, access/security, local development, promotion/deployment, exceptions, verification, migration. No fixed environment count/naming or CI/CD platform mandated.
- `dependencies.md`: dependency selection, explicit declaration/versioning, direct vs transitive dependencies, lifecycle, updates, security/vulnerability handling, license/compliance, removal, reproducibility, exceptions, verification, migration. No mandated language, package manager, registry, versioning scheme, or dependency tool.
- `documentation.md`: documentation types, ownership, discoverability, source of truth, accuracy/maintenance, architecture/design docs, operational docs, Project Context, AI-readable docs, generated docs, format/tooling, exceptions, verification, migration. Documentation is an engineering artifact; no mandated format/platform.
- `ai-entry-point.md`: authoritative AI entry point, loading order, Project Context discovery, standards discovery, authority/precedence, scope, human readability, maintenance, boundary with AI Development workflow, exceptions, verification, migration. It connects the repository to Project Context and applicable standards without duplicating the complete AI workflow.
- `standards/glossary.md`: substantive Draft defining shared SES terminology, normative language, and technology-neutral naming principles. Includes Project, System, Application, Component, Module, Service, Interface, Dependency, Configuration, Environment, Repository, Artifact, Standard, Rule, Project Context, AI Agent, AI Entry Point, Decision, Source of Truth, Environment-specific, Direct Dependency, and Transitive Dependency.
- `standards/standard-relationships.md`: substantive Draft defining Standard responsibility boundaries, conceptual dependency direction, cross-cutting ownership, conflict resolution, cross-references, and primary Rule ownership. Conceptual layers progress from Principles to Foundation to Architecture to domain/engineering practices to Quality/Operations/Maintenance; cross-standard rules should have one primary owner and avoid circular definitions.
- `standards/architecture/architecture-principles.md`: substantive Draft defining technology-independent architecture principles: architectural intent, clear responsibilities, deliberate boundaries, dependency direction, boundary-protecting interfaces, support for change, justified complexity, project constraints, traceable architectural decisions, and evolvability. Includes cross-standard relationships, exceptions, verification, and migration guidance.
- `standards/presentation/README.md` exists for UI/frontend/presentation-layer standards.
- Current work is documentation/design; no application source implementation exists.
