Framework Update / Migration Direction v1.0.0 approved by user for implementation. Principles: Framework Update is not file overwrite; flow is Detect → Analyze → Plan → Approve → Migrate → Validate → Record. Track versions independently for Framework, Blueprint, Schema, Procedure, Software Standard, and Project Context. Classify changes as no-impact, compatible, migration-required, or breaking. Create Update Assessment before changing a project. Create Migration Plan with current/target versions, changed artifacts/rules, impacted records, required migrations, source-code impact, risks, proposals, and approval needs. User is authorization boundary: AI may analyze/propose; apply only approved changes. Framework migration may modify Project Context/framework artifacts/profile/assessment/handoff after approval; source code, DB, API, UI and application changes must be separate development work. Use Migration ID to correlate changes. Version-specific migration guides belong under migrations/framework/ while generic orchestration belongs in ai_development/migration/framework-update-procedure.md. Preserve old records/traceability rather than destructive overwrite; unknown/proposed must remain explicit. Migrations must be idempotent and resumable with statuses proposed, approved, in-progress, completed, partial, blocked, rejected, cancelled, superseded. Validate schemas, references, versions, Project Context, affected Standard Assessments, and Handoff after migration. Rollback should be traceable/reversible where practical; source rollback remains separate. Existing repositories without reliable framework version must use unknown, not guess. Git history/metadata is forbidden as onboarding/migration evidence. Proposed structure: schemas/framework-update/README.md, ai_development/migration/framework-update-procedure.md, examples/framework-update/update.yaml, migrations/framework/<from>-to-<to>.md, and project-owned .project-context/framework/version.yaml plus migrations/<migration-id>.yaml.
