Software Engineering Standard — Architecture

มาตรฐาน Architecture ครบ 5 เรื่อง: intent, system boundaries, component boundaries, dependency direction และ interfaces

1. Architecture Principles

Architecture ต้องมี intent ความรับผิดชอบชัด boundaries deliberate dependencies มีทิศทาง และรองรับการเปลี่ยนแปลง

MUST: การตัดสินใจเชิงสถาปัตยกรรมที่สำคัญต้องอธิบายได้ด้วย requirements, constraints, risks หรือ quality attributes
SHOULD: หลีกเลี่ยง structure ที่เกิดจาก convention หรือความนิยมโดยไม่มีเหตุผลของโครงการ

Architecture ต้อง traceable, evolvable และไม่เพิ่ม complexity โดยไม่มีประโยชน์

2. System Boundaries

ต้องชัดเจนว่าอะไรอยู่ในระบบ อะไรเป็น external actor/system ใครรับผิดชอบ และข้อมูลใดเป็นของใคร

MUST: boundary ต้องมีเหตุผล อธิบาย external interactions, ownership และ trust/security boundary ที่สำคัญได้
SHOULD: ลด coupling และทบทวนการแยก/รวมระบบเมื่อ constraints เปลี่ยน

ไม่บังคับ Microservices, Monolith, deployment separation หรือ protocol

3. Component Boundaries

Component ต้องมี responsibility ที่ coherent และ boundary ต้องช่วยลด coupling กับ change impact

MUST: มี responsibility/ownership ชัด และการติดต่อข้าม boundary ใช้ interface หรือ contract ที่ตั้งใจ
SHOULD: ลด shared mutable state, internal-detail exposure และ unnecessary coupling

การ split/combine component ต้องมีเหตุผล เช่น responsibility, ownership, change pattern หรือ complexity

4. Dependency Direction

Dependency ต้องมีทิศทางและเหตุผล สอดคล้องกับ boundaries และควรชี้ไปยัง responsibility ที่เหมาะสมและเสถียรกว่า

MUST: significant dependency ต้องรู้ provider/consumer และ dependency ข้าม boundary ต้องผ่าน contract
SHOULD: หลีกเลี่ยง circular dependency และ coupling กับ implementation detail ที่เปลี่ยนบ่อย

Dependency inversion ใช้ได้เมื่อช่วยรักษา boundary อย่างมีประโยชน์

แยกจาก Foundation Dependencies: Foundation ดูแล selection/version/security/lifecycle; Architecture ดูแลทิศทางและความหมายของ dependency

5. Interfaces

Interface คือ contract ที่ปกป้อง boundary ต้องออกแบบจาก consumer need และไม่เปิด implementation detail ที่ไม่จำเป็น

MUST: contract ต้องมี semantics ชัด behavior สำคัญเข้าใจได้ และ validation เหมาะกับ boundary
SHOULD: มี compatibility/evolution strategy, error behavior, security และ observability ตามความเสี่ยง

ไม่บังคับ REST, GraphQL, RPC, event หรือ protocol ใด และไม่สร้าง interface เพียงเพื่อเพิ่ม abstraction
