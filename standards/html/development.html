1. Implementation Standard

เป้าหมาย

เปลี่ยน requirement และ design ให้เป็น implementation ที่ถูกต้อง เข้าใจได้ ดูแลรักษาได้ และสอดคล้องกับสถาปัตยกรรม โดยไม่ผูกกับภาษา framework หรือเครื่องมือใดเป็นพิเศษ

หลักการ

  1. สอดคล้องกับ Intent — โค้ดต้องสะท้อน responsibility และ behavior ที่ระบบตั้งใจไว้
  2. Correctness มาก่อนความสั้น — ให้ความสำคัญกับ correctness, clarity และ predictable behavior
  3. Responsibility ชัดเจน — แต่ละส่วนควรมี responsibility ที่เข้าใจได้
  4. หลีกเลี่ยงความซับซ้อนที่ไม่จำเป็น — ไม่เพิ่ม abstraction หรือ indirection โดยไม่มีประโยชน์ชัดเจน
  5. Behavior สำคัญต้องชัดเจน — business rules, เงื่อนไข และ side effects ที่สำคัญต้องระบุและเข้าใจได้
  6. ควบคุม Side Effects — state changes และ external interactions ควรอยู่ในตำแหน่งที่ตรวจสอบผลกระทบได้
  7. เคารพ Architecture — ห้ามสร้าง dependency หรือ boundary violation ที่ขัดกับ Architecture โดยไม่มี decision รองรับ
  8. จำกัด Change Impact — การเปลี่ยนแปลงควรไม่กระจายไปส่วนที่ไม่เกี่ยวข้องโดยไม่จำเป็น
  9. พิจารณา Duplication อย่างมีเหตุผล — ไม่สร้าง abstraction เพียงเพราะ code มีโครงสร้างคล้ายกัน
  10. Implementation ที่ซับซ้อนต้องมีเหตุผล — ควรมีเหตุผลใน code, documentation หรือ Decision ที่เกี่ยวข้อง

ตรวจสอบ

ตรวจ requirement, architectural intent, responsibility, complexity, boundaries, side effects และ change impact

2. Error Handling Standard

เป้าหมาย

ทำให้การตรวจจับ จัดการ ส่งต่อ และรายงาน error มี behavior ที่ predictable, diagnosable และปลอดภัย

หลักการ

  1. จัดการตามความหมาย — แยก error ที่จัดการได้ออกจาก error ที่ควรส่งต่อหรือทำให้ operation ล้มเหลว
  2. รักษา Contract — error behavior ต้องสอดคล้องกับ interface และ contract
  3. ห้ามกลบ Error สำคัญ — ห้าม silently ignore error ที่กระทบ correctness, security, data integrity หรือ operations
  4. มี Context เพียงพอ — error ควรช่วยระบุ operation และสาเหตุ โดยไม่เปิดเผยข้อมูลลับ
  5. รักษา State Consistency — คำนึงถึง partial changes, cleanup และ consistency
  6. แปลง Error ที่ Boundary — error ที่ข้าม boundary ควรเหมาะกับ contract ของ boundary
  7. Retry ต้องมีเหตุผล — retry เมื่อมีโอกาสสำเร็จเมื่อทำซ้ำ และต้องคำนึงถึง idempotency และขอบเขต
  8. ใช้กลไกที่เหมาะสม — ไม่สร้าง abstraction ที่ซับซ้อนเกินลักษณะของ error

ตรวจสอบ

ตรวจ error propagation, contract, state consistency, retry behavior และการไม่เปิดเผย sensitive information
